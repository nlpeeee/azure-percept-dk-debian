# Build the Percept USB installer with Windows and WSL

Windows is the source checkout; the WSL checkout is a separate build copy.
Only committed changes transfer through Git. Local board settings, downloads
and outputs are ignored by Git and do not transfer with a pull.

## Synchronize source

Commit reviewed files in the Windows checkout, then in WSL:

    cd ~/azure-percept-dk-debian
    git pull --ff-only origin main

The build command checks that Windows and WSL have the same source commit.
Use WSL's Linux filesystem for builds, preserving ownership and symlinks.

## Choose your installation settings

On Windows:

    python percept configure --name my-percept

The wizard collects hostname, user/password or keys, Ethernet/Wi-Fi, recovery
network and username/password, and CPU profile. Password authentication can be
enabled for both Debian and recovery. A recovery account is an administrator
with UID 0; its username need not be root. A separate recovery password can be
typed without echo. Hashes go in git-ignored secrets.toml; plaintext typed
passwords are not retained. Generated passwords are saved once in the personal
output's credentials.txt. No default password is built in.

The compatibility CPU default is unchanged. Select rated for the tested
industrial-grade 800/1300 MHz policy, or explicitly select oc1500 to reproduce
the experimentally tested 800/1300/1500 MHz policy. Keep the existing idle,
clock and domain workarounds.

## Fetch and build

    python percept fetch --recovery PATH-TO-MICROSOFT-RECOVERY.zip
    python percept build --board my-percept --target image

Windows validates and resolves local key/secret files, then sends the settings
privately over stdin to the WSL process. They are not committed or echoed in logs.
The build currently supports the Debian trixie distro-kernel image profile.
Run the same commands directly inside WSL for a Linux-only build.

Output is under WSL out/BOARD/TIMESTAMP/:

- BOARD-PERSONAL.raw: sparse GPT disk image, containing personal credentials.
- BOARD-PERSONAL.uuu: vendor-based flash script matching that disk image.
- fast-hab-fw.raw: the verified original Microsoft firmware, unchanged.
- BOARD-PERSONAL.manifest.json and SHA256SUMS: inputs, versions and hashes.
- credentials.txt: only when passwords were generated; keep private.
- build.log and work/: private build diagnostics and filesystem staging.

Never publish these personal outputs or vendor content. Re-run builds into a
new timestamp directory; the builder does not overwrite an existing disk image.

## Layout and runtime behavior

The image retains the factory reserved prefix and p1/p2/p3 roles. P1 becomes a
64 MiB ESP containing the signed stock kernel, generic launcher and both DTBs.
P2 retains the factory secondary ESP. The factory ESP partition identifiers are
preserved for the firmware boot paths. P3 is the new Debian root, with a newly
generated filesystem UUID. Unused factory root/data slots are replaced by this
single Debian root.

All root-tree operations use mapped user IDs and private mount namespaces.
The ext4 image uses 4 KiB blocks and excludes orphan_file/metadata_csum_seed.
Configured first boot can expand the final root partition to fill eMMC. Host
keys and machine-id are generated by the installed system, not copied from the
first device. Recovery persists its own host key on the ESP.

The launcher remains generic. Its credentials/settings come from ESP files,
and it captures a fresh device tree on every stock-kernel boot. The CPU profile
hook runs before final initramfs generation and filesystem packaging.

## M4 validation already completed

On 21 October 2026, source f31f195 independently rebuilt the modules and launcher
twice with byte-identical outputs. The new launcher then booted the installed
Debian 6.12.113 kernel successfully on hardware, confirmed over UART and SSH.
The failure counter reset to zero, and schedutil retained the 1500 MHz maximum.

The narrow disassembly check permits only the two reviewed preemption-counter
accesses at fixed thread_info offset 24 in kernel_kexec. That structure precedes
the randomized task fields. It rejects stack canaries and other task accesses.

This proves M4 for that artifact set. A newly composed USB image remains
unqualified until it has been flashed and booted; hardware_tested is false in
its build manifest. Cold boots, rescue and kernel-update tests are separate
acceptance steps. Use the established Microsoft factory restoration procedure.
